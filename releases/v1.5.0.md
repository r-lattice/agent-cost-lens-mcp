# Agent Cost Lens v1.5.0 — smaller uploads, agreed on first

*2026-07-30*

Client update: `pip install --upgrade agent-cost-lens-mcp` (1.3.0). Safe to do
before or after the server side — see below.

## Uploads can be compressed now

The upload is gzipped, which on real data is a **12× reduction** — measured on
9,978 records, 2.72 MB became 225 KB on the wire. Uploads finish faster and
move a lot less data, which is worth the most on a slow or metered connection.

Nothing about the data changed. The same document goes up, carrying the same
fields; it simply travels in fewer bytes. Your source and session names are
still replaced with local pseudonyms before anything leaves your machine, and
`preview_upload` still shows you the exact records that would be sent.

Compression on its own does **not** let you ask about more history — the size
limit applies to the document, not to the bytes it travels in. The limit moved
separately, below.

## The upload limit is now 15 MB

Up from 5 MB: three times the history in one request, at the record sizes
people actually push, and set just above the most a single request can carry
under the event limit below. Sizing it higher than that would have bought no
extra history — only a larger worst case for the server to absorb.

The new limit is tied to the memory the service runs with, and the server
refuses to start if the two ever disagree. That sounds like an implementation
detail and is really a promise: the limit cannot quietly be raised past what
the service can actually hold, so an over-large upload keeps getting the clean
"narrow your window" refusal instead of failing in a way that also disrupts
other people's requests.

One limit did not move: a single request still carries at most **50,000
events**, and for most people that is now the first ceiling you will meet
rather than the byte size.

## The two ends agree before compressing

The client asks the server which encodings it accepts and compresses **only**
if the server says it takes gzip. If it says nothing — because it is an older
server, or the check cannot be made at all — the client sends the same plain
upload it always has.

That means there is no upgrade order to get right. Old client to new server
works. New client to old server works. You can update whenever suits you, and
the smaller upload switches on by itself once both ends support it.

## Refusals got more precise

- A compressed upload that would expand past the size limit is now refused
  *without being expanded first*, so an oversized upload cannot tie up the
  server on its way to being rejected.
- An unrecognized `Content-Encoding` is refused by name. Previously it would
  have been read as plain text and reported as malformed JSON — an error
  message about the wrong problem.
